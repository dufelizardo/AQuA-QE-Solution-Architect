# AQuA-QE Solution Architect — Whitepaper

> Also available in [Português](WHITEPAPER.md).

> Solution architecture agent that generates Solution Design Documents (architecture pattern, components, integrations, non-functional requirements, technical risks and architecture decisions/ADRs) from a PRD (generated by the sibling AQuA-QE Product Manager agent) or equivalent requirements source — with mandatory traceability to the source, automatic validation, and human review at the center of the cycle.

Repository: [github.com/dufelizardo/AQuA-QE-Solution-Architect](https://github.com/dufelizardo/AQuA-QE-Solution-Architect)

---

## 1. Executive summary

Between "we have an approved PRD" and "we have Epics/User Stories ready for the backlog" there is a decision that today is usually made informally, in the head of whoever writes the stories: which architecture pattern to use, which components and integrations the system needs, which non-functional requirements matter and why, which technical risks exist, and which architecture decisions were made — with which discarded alternatives and why. When this decision is never explicitly recorded, that knowledge stays locked in the memory of whoever was in the conversation, and the User Stories generated from the PRD carry implicit technical assumptions that are never reviewed.

The AQuA-QE Solution Architect is an agent that structures this technical decision into a formal artifact — the **Solution Design Document (SDD)** — without removing the human decision from the process. Given a requirements source (a PRD generated by the sibling AQuA-QE Product Manager agent, a `.txt`/Markdown file, chat text, a Jira ticket, or a Confluence page), it identifies the most suitable architecture pattern (only from a closed catalog of real patterns, never invented), the components and integrations cited/inferable in the text, non-functional requirements categorized per ISO/IEC 25010 with traceable rationale, identifiable technical risks, and relevant architecture decisions as ADRs with explicit alternatives — validates automatically, submits the result to a second LLM as an independent reviewer, and only then presents it for explicit human approval. No output is approved by the agent itself.

This is the platform's third AQuA-QE agent, closing the bridge that was missing between the Product Manager (owner of the PRD) and the Product Owner (owner of Epics/Stories): "what is the best technical solution to address this business requirement?".

## 2. Methodological grounding

No quality criterion used by the agent was invented. Each one is documented in `knowledge/methodology/` and is referenced directly by the agent's rules and guardrails:

| Framework | Role in the agent |
|---|---|
| **Architecture pattern catalog** (`architecture_patterns.md`) | 14 real patterns (Layered, Hexagonal, Clean, Onion, Microservices, Modular Monolith, Event-Driven, SOA, Serverless, CQRS, Event Sourcing, BFF, API Gateway, Sidecar), each with a description, when to use it, and trade-offs — the only source `identify_architecture_pattern` may choose from (GR-SA-1). |
| **ISO/IEC 25010** (`iso25010.md`) | The 6 non-functional requirement categories `generate_non_functional_requirements` uses to categorize each identified NFR. |
| **ADR / Architecture Decision Records** (`adr.md`) | The structure (context, decision, alternatives considered, consequences) `generate_architecture_decisions` follows for every relevant architecture decision. |

These documents are not decoration: `identify_architecture_pattern` explicitly rejects (returns `""`) any LLM response not in the catalog, and the ADR format is enforced directly in the prompt of `generate_architecture_decisions`/`refine_solution_design`.

## 3. Design principles (guardrails)

Eight guardrails, originally supplied as the agent's specification and of equal priority to one another — none subordinate to the others — govern the agent's behavior (`docs/agent/guardrails.md`):

- **GR-SA-1 — Never invent functional requirements not present in the PRD.** Every component, integration, NFR, risk, or decision is traceable to the source; `identify_architecture_pattern` only chooses from the closed catalog.
- **GR-SA-2 — Never assume integrations without documented evidence.** `identify_components_and_integrations` leaves the list empty when there's no evidence, rather than assuming "every modern solution probably integrates with X". Domain-likely integrations (e.g., SUS/CNES for Brazilian public health) go into a separate field, `candidate_integrations`, always labeled as a suggestion to confirm — never mixed with confirmed integrations (RULE-SA-11).
- **GR-SA-3 — Every relevant architecture decision must have an ADR.** `validate_solution_design` rejects a Solution Design with no recorded decision.
- **GR-SA-4 — Always make trade-offs between alternatives explicit.** Every `ArchitectureDecision` has `alternatives_considered`; the prompt never presents a decision as the only possible option when that isn't the case.
- **GR-SA-5 — Don't recommend technologies incompatible with the organization's standards without recording the justification.** Partial coverage in this phase: there is not yet a source of "organization technology standards" as input — documented as a guardrail that only becomes fully verifiable in a future phase.
- **GR-SA-6 — Every NFR must be traceable to a business need or technical constraint.** `rationale` is required on every `NonFunctionalRequirement`.
- **GR-SA-7 — Never omit identified technical risks.** `identify_technical_risks` always runs, and its result is never silently discarded.
- **GR-SA-8 — Diagrams, components and contracts must remain consistent with each other.** Not applicable in this phase: diagrams (C4) and API contracts don't exist yet in the agent.
- **Cross-cutting guardrail — No automatic approval.** Regardless of the eight guardrails above being satisfied, the agent never marks a Solution Design as "approved" — only as a **validated draft** (`draft_validated`). Final approval is always a human act (same principle as GR-1 in the Product Owner and GR-M in the Product Manager).

These guardrails become formal, verifiable rules (`RULE-SA-1` through `RULE-SA-11` in `docs/agent/rules.md`).

## 4. Architecture

```
Input (.txt/Markdown/chat/Jira/Confluence)
   → read_text_file / parse_chat_transcript+format_chat_transcript (chat only) / read_jira_issue / read_confluence_page
   → extract_solution_context           (generator LLM — title + context/problem)
   → identify_architecture_pattern      (generator LLM — closed catalog only, GR-SA-1)
   → identify_components_and_integrations (generator LLM — structured by the chosen pattern, GR-SA-2)
   → identify_candidate_integrations     (generator LLM — suggestions to confirm, RULE-SA-11)
   → identify_domain_model               (generator LLM — entities/attributes, GR-SA-1)
   → identify_process_flows              (generator LLM — flows/steps, GR-SA-1)
   → generate_non_functional_requirements  (generator LLM — ISO/IEC 25010, GR-SA-6)
   → identify_technical_risks            (generator LLM — GR-SA-7)
   → generate_architecture_decisions     (generator LLM — ADRs with alternatives and positive/negative consequences, GR-SA-3/GR-SA-4)
   → validate_solution_design            (pure Python checklist)
   → review_solution_design              (independent reviewer LLM — phi4)
   → [if rejected] generate_sdd_clarifying_questions → human answer → refine_solution_design → revalidate
   → explicit human acceptance
   → format_solution_design_markdown
```

Unlike the Product Owner (which processes in two phases — Epic first, Stories second — to avoid spending expensive processing before the Epic itself is defined), the Solution Architect processes in a single pass: there's no intermediate unit expensive enough to justify a reception checkpoint before full generation. `validate_solution_design` runs before `review_solution_design` for the same cost reason already established in PM/PO — never pay the reviewer LLM's cost for a Solution Design that already fails the automatic checklist.

Code layers (`src/aqua_qe_solution_architect/`):

- **`models/`** — data structures: `SolutionDesign`, `NonFunctionalRequirement`, `ArchitectureDecision`, `DomainEntity`, `ProcessFlow`, and the `ArtifactStatus` enum (`draft_validated` / `pending_clarification` / `accepted`).
- **`skills/`** — 22 functions, each with a single side effect and a single responsibility (see section 5).
- **`workflow/generate_solution_design.py`** — `generate_solution_design` (generates the SDD from scratch from the text) and `finalize_solution_design` (applies validate→review, also reusable after `refine_solution_design`).
- **`orchestrator/solution_architect.py`** — single entry point (`handle_request(entrada)`).
- **`services/`** — external integrations: `llm_service` (Ollama), `jira_service` (REST API + httpx, **read-only**), `confluence_service` (REST API + httpx, **read and write** — writes always gated behind explicit human confirmation, see section 8).

Deliberately **not present** in this phase: a C4 diagram generation/rendering layer, an API/OpenAPI contract parser, UML/BPMN/Swagger/DB-schema parsers, and the 7 additional pattern categories (design/integration/distributed/cloud/security/data) + anti-patterns library that were part of the agent's original full specification. Each of these has real value, but depends on a real consumer that doesn't exist yet (same "don't build without a consumer" principle already applied to the Product Owner's `Feature` layer) — see section 11.

## 5. The 22 skills

Skills without an LLM (pure Python, deterministic):

- `validate_solution_design` — checklist: title, context, architecture pattern with rationale, at least one NFR, at least one architecture decision.
- `format_solution_design_markdown` — exports the Solution Design Document to Markdown, sections per `knowledge/templates/solution_design.md`.
- `parse_chat_transcript`/`format_chat_transcript` — recognize and normalize multi-sender chat transcripts in the `--texto` input, leaving plain text with no identifiable sender unchanged.

Skills with a generator LLM (`OLLAMA_MODEL`, default `mistral`):

- `extract_solution_context`, `identify_architecture_pattern`, `identify_components_and_integrations`, `identify_candidate_integrations`, `identify_domain_model`, `identify_process_flows`, `generate_non_functional_requirements`, `identify_technical_risks`, `generate_architecture_decisions`, `generate_sdd_clarifying_questions`, `refine_solution_design`.

Skills with an independent reviewer LLM (`OLLAMA_REVIEW_MODEL`, default `phi4` — deliberately a different model from the generator, to mitigate self-preference bias):

- `review_solution_design`.

External I/O skills:

- `read_text_file` (disk), `read_jira_issue`/`read_confluence_page` (read-only, Jira/Confluence Cloud REST API — **no writes to Jira in this phase**, unlike the Product Owner, which also creates/updates tickets).
- `get_confluence_publish_location`, `create_confluence_page`, `update_confluence_page` — **writes** to Confluence Cloud (section 8), always behind explicit human confirmation in the CLI.

Full input/output/error detail for each skill is in `docs/agent/skills.md`.

## 6. The interactive refinement cycle

The same core principle from the Product Owner applies here: when review flags a problem, the agent doesn't try to self-correct by guessing the right answer.

1. A Solution Design arrives rejected with `review_notes` populated one of two ways: `validate_solution_design` rejects the automatic checklist and records the specific reasons (e.g., "no architecture decision (ADR) recorded") — without spending an LLM reviewer call; or, if the checklist passes, `review_solution_design` rejects with concrete findings (e.g., "the chosen pattern doesn't justify the high-availability requirement cited in the PRD", "the messaging decision doesn't record the alternatives considered"). Either way, the user always sees the exact reason — never just a status with no explanation.
2. `generate_sdd_clarifying_questions` turns each finding into a direct, actionable question.
3. The CLI (`run.py --refinar`) presents the questions in the terminal; **a real human answers**.
4. `refine_solution_design` rewrites the affected fields using the answers as real context — preserving the text/level of detail of fields the answers don't address (the same care built in from the start of this project, learned from a real bug fixed in `refine_prd`/`refine_epic_metadata` in the Product Owner).
5. The cycle revalidates (`validate_solution_design`/`review_solution_design`) and repeats if needed.
6. At the end, a prompt explicitly asks whether the user **accepts** the Solution Design. Only this explicit acceptance changes the status to `accepted` — never the LLM, never the automatic checklist (RULE-SA-9).

## 7. Modes of operation

- **Single input, single artifact** (`run.py`, no `--modo`) — unlike PM/PO, this agent has no multiple operating modes in this phase: it takes one source (`--arquivo`/`--texto`/`--jira`/`--confluence`) and produces a single Solution Design Document. The CLI always asks "Accept this Solution Design?" before exporting — only declining acceptance blocks the export.
- **`--refinar`** — turns on the question/refinement cycle (section 6), when the Solution Design isn't approved on review, before final acceptance (which is always asked, with or without this flag).
- **`--publicar-confluence`/`--atualizar-confluence`** (mutually exclusive, only valid with `--confluence`) — run after acceptance; see section 8.

## 8. Real integrations

- **Jira Cloud** (REST API v3) — read-only (`read_jira_issue`, converting Atlassian Document Format to plain text). No writes in this phase — there is no real write-back use case from a Solution Design today.
- **Confluence Cloud** (REST API v1) — page read (`read_confluence_page`, converting storage format XHTML to plain text via the stdlib's `html.parser.HTMLParser`) **and write** (`create_confluence_page`/`update_confluence_page`, converting Markdown back to storage format via a minimalist converter — only handles `#`/`##`/`###` and `- ` lists, enough for `format_solution_design_markdown`'s output). Writes are always behind explicit human confirmation (RULE-SA-10) and always create the page as a **sibling** of the PRD's source page: `get_confluence_publish_location` derives the space and immediate ancestor directly from the source page (no new environment variable needed, unlike PM/PO, which require `CONFLUENCE_SPACE_KEY`) — this guarantees by construction that the Solution Architecture Document is never published to an arbitrary location or overwriting the PRD.

## 9. Technical stack

- **Local LLM via Ollama (default)** — `mistral` for generation, `phi4` as the independent reviewer. Deliberate choice of local models over cloud APIs, configurable via `OLLAMA_MODEL`/`OLLAMA_REVIEW_MODEL`/`OLLAMA_BASE_URL`.
- **NVIDIA NIM provider pilot via toggle** (`LLM_PROVIDER=ollama|nvidia`) — same pilot already validated live in the sibling AQuA-QE Product Manager agent, replicated here: `build.nvidia.com` (OpenAI-compatible API) as an optional generator/reviewer alternative (`deepseek-ai/deepseek-v4-pro`/`meta/llama-3.3-70b-instruct`, confirmed working), preserving the two-independent-models principle. Ollama remains the unchanged default when `LLM_PROVIDER` is unset.
- **`uv`** for dependencies — standalone project (own repository, outside the monorepo that originated it), with `httpx` and `python-dotenv` explicitly declared in `pyproject.toml`.
- **Python 3.12+**, `src/` layout.
- **No vector database/RAG in this phase** — `knowledge/methodology/` has only 3 files, small enough to fit directly in each skill's prompt without needing semantic search (see section 11 and `docs/agent/context_engineering.md`).

## 10. Quality and test coverage

59 automated tests cover every implemented module, all with Ollama/Jira/Confluence calls mocked — fast, deterministic, no dependency on external infrastructure to run in CI. Evaluating the agent in production combines three layers that never replace one another (`docs/agent/evaluation.md`):

1. Automatic checklist (`validate_solution_design`) — no LLM.
2. LLM-as-judge (`review_solution_design`) — a different model from the generator.
3. Mandatory human review — the only act that actually approves an artifact.

## 11. What's still missing (deliberately deferred, not forgotten)

When specifying this agent, the user provided a mature, complete product vision (14 responsibilities, ~9 methodology categories, 8 pattern categories + anti-patterns, 20+ artifacts, 12+ input sources, 15+ external systems). Phase 1 deliberately implements only the core — generating the Solution Design Document from text — following the same principle already applied to PM/PO: build incrementally, one real consumer at a time, never speculatively. Left for future phases:

- **C4 diagrams** and any visual architecture generation/rendering — GR-SA-8 (consistency between diagrams/components/contracts) only becomes fully verifiable once this artifact exists.
- **API/OpenAPI/AsyncAPI/GraphQL contracts** — no contract parser or generator exists in this phase.
- **UML/BPMN/Swagger/DB-schema parsers** — as additional input sources.
- **The 7 additional pattern categories** (design/integration/distributed/cloud/security/data) **and the anti-patterns library** — only the architecture pattern catalog (the category most directly needed by `identify_architecture_pattern`) was built in this phase.
- **Real write integrations** — Jira write-back, GitHub, GitLab, Kubernetes, Terraform, cloud providers (AWS/Azure/GCP) — none has a real consumer today within Phase 1's scope (Confluence write-back has already been implemented, section 8).
- **`--sdd-existente`** (inverse parser for the exported Markdown) — the same pattern by which `--epic-existente`/`--story-existente` were built as a *later* increment on top of the base features in the Product Owner, not from day one.
- **GR-SA-5** (compatibility with the organization's technology standards) — there is no "organization standards" input source today; the guardrail is documented, but only fully verifiable once that source exists.
- **RAG/project memory** (`docs/agent/memory.md`) — `knowledge/methodology/` has only 3 files in this phase, small enough to fit directly in the prompt without semantic search; RAG is left for when the pattern catalog grows large enough to no longer fit.
- **Formal architecture description/evaluation frameworks** (TOGAF, Zachman, Arc42, ISO/IEC/IEEE 42010, ISO/IEC 12207, QAW, ATAM) — cited in the agent's original specification to ground how to formally document and evaluate an architecture; none were adopted in this phase (`knowledge/methodology/` covers only what the current scope needs). Adopting them without a real consumer (e.g., a client requiring formal Arc42 documentation) would be speculative.

## 13. Conclusion

The AQuA-QE Solution Architect doesn't aim to replace the solution architect — it aims to eliminate the mechanical work of structuring a technical decision that, without it, would stay implicit in the head of whoever writes the stories derived from the PRD. Every guardrail in the project (never invent, never omit a risk, always justify trade-offs, never approve alone) exists so that the agent's output is always a reliable starting point for human review, never a substitute for it. Phase 1, deliberately restricted to the core, is the first increment of a much larger product vision — built, like the platform's other two agents, one real consumer at a time.
