# Agent Design

> Estrutura conforme `../standards/agent_design_standard.md`. Decisões de design centrais do agente.

1. **Um único artefato nesta fase** — diferente de PM (4 artefatos: descoberta/visão/estratégia/PRD) e PO (Story/Epic), o Solution Architect gera só o Solution Design Document nesta fase. Simplifica o CLI (sem `--modo`) e o orquestrador (uma única sequência de skills).
2. **Prosseguir vs. interromper por ambiguidade** — após `identify_architecture_pattern`/`identify_components_and_integrations`/`generate_non_functional_requirements`, o agente avalia se há informação suficiente para um Solution Design rastreável e completo. Se não houver (ex.: nenhum NFR identificável, nenhuma decisão registrável), `validate_solution_design` reprova e o ciclo de refinamento entra em ação — nunca se preenche a lacuna com uma suposição silenciosa (GR-SA-1).
3. **Padrão arquitetural restrito a um catálogo fechado** — diferente de campos livres como `title`/`context_problem`, `architecture_pattern` só pode ser um dos itens listados em `knowledge/methodology/architecture_patterns.md`. Essa é a decisão de design mais importante do agente: um "arquiteto" que pudesse inventar padrões livremente perderia a garantia de que toda recomendação é rastreável a uma prática real e documentada (GR-SA-1).
4. **Aprovar automaticamente vs. exigir revisão humana** — o agente **nunca** decide aprovação final. `validate_solution_design` decide apenas se o Solution Design passa no checklist automático (nível "rascunho validado"); a aprovação de negócio/técnica permanece sempre humana.
5. **Trade-offs sempre explícitos, nunca implícitos** — `alternatives_considered` em cada `ArchitectureDecision` não é opcional por acaso: reflete GR-SA-4 (nunca apresentar uma decisão como se fosse a única opção possível quando não for o caso). A skill de geração é instruída a listar alternativas sempre que existirem; a ausência de alternativas é aceitável só quando genuinamente não havia outra opção viável — julgamento que cabe à revisão humana/LLM, não ao checklist automático (por isso RULE-SA-4 é recomendação, não bloqueante).
6. **`estimate`/tecnologias específicas de implementação ficam fora** — o agente recomenda um **padrão** arquitetural (ex.: Microservices), não uma stack de tecnologias específicas (ex.: "usar Kafka na versão X") — decisão deliberada para não expandir prematuramente para o catálogo completo de tecnologias antes de haver demanda real (mesmo princípio de "não construir especulativamente" já usado em PM/PO).
